# バグ作成フロー

## 前提

バグ Issue は、運用中に発見された不具合や仕様との乖離を起票するための Issue。
受け入れ基準は「修正の確認」と「再発防止」の 2 軸で構成する。

## Step 1: テンプレート読み込み

以下のファイルを Read して、フィールド構造（label / value / required）を把握する:

- `.github/ISSUE_TEMPLATE/bug.yml`

このテンプレートのフィールドに沿って、最終プレビューと Issue 本文を組み立てる。

## Step 2: バグ内容の入力

`AskUserQuestion` ツールは使わず、テキストで以下を順に聞く（各ステップでユーザーの自然言語回答を得る）:

1. `どんなバグが起きていますか？（現象を自然な日本語で記述してください）`
2. `再現手順を教えてください。（番号付きで、誰でも同じ操作で再現できる粒度でお願いします）`
3. `本来どうあるべきですか？（期待される挙動）`
4. `実際にはどうなっていますか？（実際の挙動。エラーメッセージや画面の状態を含めてください）`

→ 1 の回答からタイトルを以下の形式で組み立てる:

```
[バグ] <バグ内容>
```

組み立てる際の注意:

- 「<バグ内容>」は現象を端的に表す日本語にする（例: `保存ボタン押下時にエラーが発生する`）
- 「〜という不具合」「〜のバグ」のような冗長な接尾辞は付けない

例:

- 入力: `プロジェクト編集画面で保存を押すと500エラーが返る`
  → `[バグ] プロジェクト編集画面で保存ボタン押下時に500エラーが発生する`

## Step 3: 発生環境の選択

`AskUserQuestion` を **1 回だけ呼び出し**、以下の 3 つの質問を `questions` 配列にまとめて渡す（ユーザーは 1 画面で 3 問まとめて選択 → submit する）。すべて複数選択可:

1. 質問: `発生しているブラウザを選んでください`
   - 選択肢: `Chrome` / `Safari` / `Firefox` / `Edge`
   - `multiSelect: true`
2. 質問: `発生しているデバイスを選んでください`
   - 選択肢: `PC` / `スマートフォン` / `タブレット`
   - `multiSelect: true`
3. 質問: `発生している環境を選んでください`
   - 選択肢: `local` / `dev` / `prod`
   - `multiSelect: true`

ユーザーが `Other` で追加入力した場合は、その内容も発生環境に含める。

## Step 4: 頻度の選択

`AskUserQuestion` ツールで以下を聞く:

- 質問: `このバグの発生頻度を教えてください`
- 選択肢:
  1. `常に再現する`
  2. `特定条件下で再現する`
  3. `散発的に発生する`
- `multiSelect: false`

## Step 5: 参照コードの指定

ユーザーに以下を聞く:

```
バグが発生しているファイルのパスが分かれば教えてください。
（複数可、なければ「なし」と答えてください）
※ ディレクトリ単位の指定は不可。ファイル単位で指定してください。
```

指定されたパスを **ファイルのみ Read** する。ディレクトリが指定された場合は、その旨を伝えて代表的なファイルを指定し直してもらう（大量ファイルを一括読み込みしないため）。

## Step 6: 中間確認【1 回目の確認ポイント】

ここまでの入力内容（タイトル / バグ概要 / 再現手順 / 期待挙動 / 実際の挙動 / 発生環境 / 頻度 / 参照コード）をまとめて提示し、`AskUserQuestion` で以下を聞く:

- 質問: `この内容で受け入れ基準の草案作成に進みます。よろしいですか？`
- 選択肢:
  1. `OK で進める`
  2. `修正したい箇所がある`

`修正したい箇所がある` が選ばれた場合は、何をどう変えるかをテキストで聞き、該当部分のみ反映してこの Step を再実行する（**OK が出るまでループ**）。

## Step 7: AI による草案生成

ユーザー入力と参照コードを踏まえて、`bug.yml` のフィールド構造に沿って以下を生成する:

- **バグの概要（整文版）**: ユーザー入力を 1〜2 行に要約
- **再現手順（整文版）**: 番号付きで、抜け漏れがあれば補完
- **期待される挙動（整文版）**: 本来の振る舞いを明確に
- **実際の挙動（整文版）**: 観測された現象を具体的に
- **発生環境**: ブラウザ / デバイス / 環境（local / dev / prod）を Markdown 箇条書きで整形
- **頻度**: 選択結果をそのまま記載
- **受け入れ基準**: `bug.yml` の `value` に含まれるデフォルト 4 行を保持しつつ、バグ固有の検証項目が必要であれば先頭に追加する
  - デフォルト行: `再現手順を実行しても期待挙動になっている` / `リグレッションテストを追加している` / `単体テストが通過している` / `結合テストが通過している`

## Step 8: 最終プレビュー【2 回目の確認ポイント】

`bug.yml` のフィールド構造（label）に沿って Markdown 本文を組み立て、タイトル含めて表示する:

```markdown
タイトル: [バグ] <バグ内容>

## バグの概要

<整文版>

## 再現手順

1. ...
2. ...
3. ...

## 期待される挙動

<整文版>

## 実際の挙動

<整文版>

## 発生環境

- ブラウザ: ...
- デバイス: ...
- 環境: ...

## 頻度

<選択結果>

## 受け入れ基準

- [ ] ...
- [ ] 再現手順を実行しても期待挙動になっている
- [ ] リグレッションテストを追加している
- [ ] 単体テストが通過している
- [ ] 結合テストが通過している
```

`AskUserQuestion` で以下を聞く:

- 質問: `この内容で Issue を作成します。よろしいですか？`
- 選択肢:
  1. `OK で作成`
  2. `修正したい箇所がある`

`修正したい箇所がある` が選ばれた場合は、何をどう変えるかをテキストで聞き、該当フィールドのみ反映してこの Step を再実行する（**OK が出るまでループ**）。

## Step 9: Issue 作成

`gh repo view --json nameWithOwner -q .nameWithOwner` で現在のリポジトリ名を取得し、`AskUserQuestion` で以下を聞く:

- 質問: `<owner>/<repo> に Issue を作成します。よろしいですか？`
- 選択肢:
  1. `OK`
  2. `中止`

OK が出たら `gh issue create` で Issue を作成する（`--repo` は付けない。現在のリポジトリに作成される）:

```bash
gh issue create \
  --title "<組み立てたタイトル>" \
  --body "<組み立てた本文>"
```

成功したら、作成された Issue の番号と URL をユーザーに表示して終了する。
