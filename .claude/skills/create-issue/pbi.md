# PBI 作成フロー

## 前提

PBI（Product Backlog Item）は、PO が作成するユーザーストーリー単位の Issue。
受け入れ基準は結合テストのテストケースと 1:1 対応する粒度で記述する。

## Step 1: テンプレート読み込み

以下のファイルを Read して、フィールド構造（label / value / required）を把握する:

- `.github/ISSUE_TEMPLATE/pbi.yml`

このテンプレートのフィールドに沿って、最終プレビューと Issue 本文を組み立てる。

## Step 2: タイトル構造化入力

`AskUserQuestion` ツールは使わず、テキストで以下を順に聞く:

1. `ユーザーは誰ですか？（例: ログイン済みユーザー、管理者、未ログインユーザー）`
2. `そのユーザーは何ができるようになりますか？（目的・行動）（例: 商品をカートに追加する）`

→ 回答内容を踏まえて、ユーザーストーリー形式（`<ユーザー> として、<目的 / 行動>`）の自然な日本語タイトルを組み立て、ユーザーに提示する。
※ ユーザー部分を `[]` で囲わないこと。

組み立てる際の注意:

- 機械的にテンプレートに当てはめない（語尾が二重になり不自然な日本語になる）
- 入力された目的・行動の語尾に合わせて文末を整える:
  - 入力が「〜する」で終わる動詞句 → 「〜できる」に変換する（例: 「編集する」→「編集できる」）
  - 入力が体言（名詞）で終わる → 「〜ができる」を付ける（例: 「プロジェクトの編集」→「プロジェクトの編集ができる」）
  - 入力がすでに「〜できる」で終わる → そのまま使う

例:
- ユーザー: `ログイン済みユーザー` / 目的: `プロジェクト一覧からプロジェクトを編集する`
  → `ログイン済みユーザー として、プロジェクト一覧からプロジェクトを編集できる`
- ユーザー: `管理者` / 目的: `部署マスタの一括登録`
  → `管理者 として、部署マスタの一括登録ができる`

## Step 3: 参照ソースの収集

### 3-1. PRD 必読

`docs/prd.md` を **無条件で Read** する（必須）。
ファイルが存在しない場合は、ユーザーにその旨を伝え、PRD なしで続行するか確認する。

### 3-2. ADR の指定

ユーザーに以下を聞く:

```
関連する ADR ファイルがあれば、ファイル名を教えてください。
（docs/adr/ 配下の複数ファイル可、なければ「なし」と答えてください）
```

指定されたファイルを Read する。

### 3-3. 参照コードの指定

ユーザーに以下を聞く:

```
参照させたい既存コードのファイルパスがあれば教えてください。
（複数可、なければ「なし」と答えてください）
※ ディレクトリ単位の指定は不可。ファイル単位で指定してください。
```

指定されたパスを **ファイルのみ Read** する。ディレクトリが指定された場合は、その旨を伝えて代表的なファイルを指定し直してもらう（大量ファイルを一括読み込みしないため）。

## Step 4: Why / What の素案受付

ユーザーに以下を提示し、箇条書きで素案を出してもらう:

```
Why（なぜこれが必要か）と What（具体的に何を実現するか）を箇条書きで素案してください。
PRD・ADR・参照コードを踏まえて AI が整えます。
不明な点は「不明」「調査必要」と書いてください。

Why:
-

What:
-
```

## Step 5: 中間確認【1 回目の確認ポイント】

ここまでの入力内容（タイトル / 参照ソース / Why・What 素案）をまとめて提示し、`AskUserQuestion` で以下を聞く:

- 質問: `この内容で受け入れ基準の草案作成に進みます。よろしいですか？`
- 選択肢:
  1. `OK で進める`
  2. `修正したい箇所がある`

`修正したい箇所がある` が選ばれた場合は、何をどう変えるかをテキストで聞き、該当部分のみ反映してこの Step の確認を再実行する（**OK が出るまでループ**）。

## Step 6: AI による草案生成

`docs/prd.md`・指定された ADR・参照コード・Why/What 素案を踏まえて、`pbi.yml` のフィールド構造に沿って以下を生成する:

- **Why（背景・目的）**: 素案を踏まえ、PRD・ADR の文脈を補って整理
- **What（詳細）**: 同上、UI・データ・挙動の要件を具体に書く
- **受け入れ基準**: 文体ガイドに従い、正常系 / 異常系 / 境界 の 3 区分で記述
  - `pbi.yml` の `value` に含まれるデフォルト行（`ADR、docs フォルダ以下のドキュメントを更新している` / `単体テストが通過している` / `結合テスト（ユーザーストーリー単位）が通過している`）は末尾に保持する
- **スコープ外**: PRD から「やらない」と読み取れる範囲、または誤解を招きそうな項目を抽出（該当なしなら空欄）

## Step 7: 最終プレビュー【2 回目の確認ポイント】

`pbi.yml` のフィールド構造（label）に沿って Markdown 本文を組み立て、タイトル含めて表示する:

```markdown
タイトル: <ユーザー> として、<目的 / 行動> ができる

## Why（背景・目的）
<整文版>

## What（詳細）
<整文版>

## 受け入れ基準
正常系:
- [ ] ...

異常系:
- [ ] ...

境界:
- [ ] ...

- [ ] ADR、docs フォルダ以下のドキュメントを更新している
- [ ] 単体テストが通過している
- [ ] 結合テスト(ユーザーストーリー単位)が通過している

## スコープ外
<該当なしなら空欄>
```

`AskUserQuestion` で以下を聞く:

- 質問: `この内容で Issue を作成します。よろしいですか？`
- 選択肢:
  1. `OK で作成`
  2. `修正したい箇所がある`

`修正したい箇所がある` が選ばれた場合は、何をどう変えるかをテキストで聞き、該当フィールドのみ反映してこの Step を再実行する（**OK が出るまでループ**）。

## Step 8: Issue 作成

`gh repo view --json nameWithOwner -q .nameWithOwner` で現在のリポジトリ名を取得し、`AskUserQuestion` で「`<owner>/<repo>` に Issue を作成します。よろしいですか？」と確認する。

OK が出たら `gh issue create` で Issue を作成する（`--repo` は付けない。現在のリポジトリに作成される）:

```bash
gh issue create \
  --title "<組み立てたタイトル>" \
  --body "<組み立てた本文>"
```

成功したら、作成された Issue の番号と URL をユーザーに表示して終了する。
